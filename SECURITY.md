# Security boundaries

This is an initial internal-team application, not a security certification or a replacement for an independent review. No software can promise complete security. Do not expose it to the public internet. Restrict it to your approved LAN/VPN and keep the OS, Git, Nginx, and self-contained .NET runtime patched.

## Access model

- Roles: **Admin** accounts can see every repository, push to every repository, create repositories and manage permissions. **User** accounts (formerly "Reader") have only the permissions granted to them.
- Per repository, each User has **none**, **read** (browse, clone, fetch/pull) or **write** (read + push). Permissions live in `/srv/privategit/access/access.json` (gitdash-owned, group-readable by `gitrepos`, no secrets). They are enforced by the dashboard on every repository page and by the SSH gate on every connection. Changes apply immediately.
- Users without read permission get **404 Not Found** for that repository, both on the web and over SSH. Missing and forbidden repositories are indistinguishable.
- SSH identity: every connection to the `git` account runs `PrivateGit git-serve` through `ForceCommand` (no shell, forwarding, PTY, scp/sftp or arbitrary command). With `ExposeAuthInfo`, the gate learns the exact public key that authenticated and maps it to one user through the `privategit:USER` marker in the root-owned `authorized_keys`. Keys without a marker, keys linked to two users, or multi-key authentication are refused. The repository name must match `^[a-z][a-z0-9_-]{0,62}$`. Only `git-upload-pack` (read) and `git-receive-pack` (write) are started, with fixed argument arrays; `git-upload-archive`, paths, options and shell syntax are rejected.
- `add-client.sh` accepts only validated Ed25519 public keys for existing accounts, refuses linking one key to two people, and adds `from="…"` network limits (per key with `--from`). `admin.sh user-delete` removes the account, its permissions and its keys.
- SSH key provisioning remains an operating-system administrator action; there is no web endpoint to change keys, run commands, delete repositories, or upload files. Web administrators manage repository permissions only.
- Git writes travel through OpenSSH, not the web application. SSH uses keys; web login uses passwords plus TOTP. A web session cannot push; a key cannot browse the dashboard. TOTP is not phishing-resistant. A compromised client or authorized account can still disclose source code or push malicious source.
- Repository contributors are trusted team members. Bare Git is not a sandbox for hostile repositories. Git patches, filesystem permissions, resource limits, and network restrictions remain necessary.

## Implemented controls

- ASP.NET Core cookie authentication; HTTP-only, SameSite Strict cookies, Secure in production; fixed four-hour sessions. Account stamp validation revokes sessions after reset/deletion.
- ASP.NET Core Identity password hashing with 600,000 PBKDF2 iterations; 16-character password minimum. No default accounts or public signup.
- Mandatory RFC 6238 TOTP; previous/current/next 30-second window; accepted steps stored to prevent replay. Five failed attempts lock an existing account for 15 minutes. Generic login errors; app and Nginx login rate limits.
- Razor antiforgery tokens on POST forms, server-side authorization, no GET mutations, and Razor HTML encoding for all repository content. Source is always text; no Markdown/HTML execution or external assets.
- CSP disallows scripts, framing and third-party resources; no-store responses; production HTTPS enforcement, HSTS, exact allowed hostname, loopback Kestrel, explicitly enabled loopback proxy trust.
- No shell invocation for Git. ArgumentList, strict repository names, hash-only object operations, no revision strings supplied to Git, symlink repository root rejection, bounded output and file previews, 12-second command deadlines, four concurrent Git processes, disabled hooks for dashboard Git commands.
- History/diff pages resolve branch/tag choices to full commit hashes before Git operations. Diff external commands and textconv are disabled; file history uses literal pathspecs after `--`. Patches and commit/tag metadata are rendered through Razor encoding, never raw HTML. Diffs have a 200-file preview limit, bounded total output, and 256 KiB / 5,000-line per-file previews. Full line totals come from Git's numstat rather than the truncated display. Binary files do not get fabricated line totals.
- Production application files and SSH authorized keys are owned by root. Dashboard and SSH have separate accounts and a shared repository group. systemd limits privileges, writable paths, tasks, and memory.
- Authentication success/failure and web repository creation go to normal application logs. SSH authentication is recorded by sshd. The SSH gate logs each allowed or denied clone/fetch/push (user, repository, operation, client IP) to syslog as `privategit-ssh`, readable with `journalctl -t privategit-ssh`. This is **not** a tamper-proof audit system and does not record individual ref updates.

## Hidden main-branch backups

After every push that changes a repository's main branch, the root-owned post-receive hook copies main into `/srv/privategit/backups/REPO.git` and adds a timestamped snapshot ref (`PrivateGit__MainBackup`, on by default). That folder is `root:gitrepos 2770`, outside the directory the SSH gate and dashboard serve, so no user can list, clone or change it through PrivateGit or as a normal Linux user. Only root, the dashboard and git service accounts, and administrators using `admin.sh` can reach it. A failed backup never blocks a push (a warning is shown and logged). The optional NAS copy (`PrivateGit__NasBackupDirectory`) is never on the critical path. The SSH gate does not touch the NAS. The hook starts the copy fully detached, at most one per repository at a time, with a hard time limit. The installer never uses the NAS, and admin commands probe it for at most 10 seconds and then skip it. Whoever can read the NAS share can read those copies, and the NAS credentials file must stay root-only (0600). Backups contain main only, not other branches, accounts or permissions.

## State and operating limitations

Account data contains password hashes and **unencrypted TOTP seeds**. Data Protection keys are persisted on disk and protect cookie contents; they are not themselves encrypted at rest. Protect `/var/lib/privategit` with mode 0700, encrypted disks/backups where appropriate, and tightly controlled root access. Theft of both account state and application keys is a security incident; reset affected credentials and keys.

The file account store is for one application instance only. A process-level file lock prevents concurrent instances/CLI changes; stop the service before account administration. Atomic file replacement prevents partial JSON files but does not provide a distributed database or guaranteed durability after power loss. Keep tested backups.

Rate limiting and lockout can be used for denial of service; a LAN/VPN allowlist is the first perimeter. In-memory IP limits reset on restart; account lockouts persist. Resource limits do not cap repository disk growth or all SSH Git work. Set storage quotas and suitable SSH per-user/session limits on the server. Logs should be shipped to an administrator-controlled destination if audit integrity matters.

No automated dependency vulnerability feed, SSO, password recovery by email, recovery codes, per-branch permissions (beyond the protected main branch), group/team objects, signed-commit enforcement, branch review protection, or high availability is included. Permissions are per user and per repository. MFA reset requires administrator console access. Pushes that rewrite history (non-fast-forward) are refused. A branch may be deleted (over SSH or in the dashboard) only by the user who created it, while they have write access, or by an administrator. The main (default) branch can never be deleted, and tag deletion is refused. The creator is recorded at branch creation by a root-owned post-receive hook as `branch.<name>.privategitowner` in the repository config, which users cannot write. Branches without a record are admin-only. Over SSH the rule is enforced by a root-owned pre-receive hook in `/opt/privategit/hooks` (per-repository hooks never run on push), and deletion is disabled automatically if that hook is missing. `PrivateGit__AllowBranchDelete=false` disables it entirely. These are guardrails, not a review policy. The dashboard is read-only for source content, but its service account necessarily has repository write access to create repositories.

## Before use

The guided `install.sh` is for a fresh Ubuntu 22.04 or 24.04 system or an installation previously owned by this installer. It validates hostname/IP/CIDR input, executable architecture, trusted TLS chain, DNS or IP SAN and certificate/key match, refuses unrelated existing identities/paths, restricts the Git SSH account to approved networks, and verifies effective SSH authentication/forwarding settings before reloading. It can install missing OS packages from the server's configured apt repositories during setup; `--offline` disables downloads. It does not alter the company's administrator SSH policy or firewall rules. `add-client.sh` accepts only validated Ed25519 public keys linked to an existing user, adds source-network and forwarding restrictions, and never accepts private keys. With the private CA option, the CA key stays root-only in `/etc/privategit/ca`; anyone holding it could impersonate the server to clients that trust it, so protect it like the TLS key and do not copy it to clients (clients only need `privategit-ca.crt`). Installer backups include sensitive TLS configuration and must remain root-only. They do not replace coordinated repository/account backups. The scripts require on-site Linux verification before production use.

1. Follow the Linux deployment guide, including TLS, firewall allowlists, root-owned app/SSH files, service isolation, and correct DNS.
2. Verify Windows and Linux trust the internal TLS CA and verify the SSH host fingerprint out of band.
3. Verify server and authenticators have accurate clocks. Enroll unique credentials; never use test credentials.
4. Run the included tests, inspect effective Nginx/sshd configuration, and test denial from an unapproved client.
5. Independently review and test the deployed Linux environment before trusting it with valuable source code. Windows tests do not verify Linux permissions, systemd, TLS, firewall rules, or SSH policy.
6. Rebuild/redeploy self-contained binaries for .NET security updates; installing a newer system runtime does not patch a self-contained binary.
